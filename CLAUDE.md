# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

GullyEats is a QR-based ordering platform for street food carts. It's a monorepo of five independent projects with no shared tooling or root package. Run commands from inside each project directory.

| Dir | Stack | Purpose |
|---|---|---|
| `backend/` | Node (CommonJS), Express 5, Mongoose, Socket.IO | Single API for all clients |
| `frontend/` | Flutter (package `gullyeats`) | **Onboarding** app, used by GullyEats staff (not vendors) to onboard a vendor: OTP login for the vendor's number (opens on Your Carts while that vendor is still logged in; back from Your Carts, or a 401 from the server, logs out to sign-up), create or resume a cart, photo, location, menu, staff, QR poster |
| `ordering/` | Flutter (package `ordering`) | **Vendor ordering** app: live orders, serve/paid toggles, sales charts, platform-fee payment via Razorpay |
| `customer-app/` | React 19 + Vite 8 + Tailwind 4 + Redux Toolkit (React Compiler enabled) | Customer web app opened from a cart's QR code (`/c/:cartId/...`). Dark theme by default, switchable from every top bar: use the colour tokens in `src/index.css` (`bg-surface` for cards, `bg-ink` for dark chips), never `bg-white`/`bg-grey-900`, so both themes work |
| `gullyeats-admin/` | React 18 + Vite 5 + Tailwind 3 + Redux Toolkit, Recharts, Leaflet | Super-admin dashboard |

## Commands

```bash
# backend (needs backend/.env, see backend/.env.example). Local work, e2e and device tests use the DEV database
# gullyeats_dev (Atlas user gullyeats_dev, readWrite on that DB only) and Razorpay test keys; production
# (DB gullyeats, live keys, its own JWT_SECRET) is configured only in Render's environment. Seed a fresh dev DB with
# node scripts/seed-food-names.js and node scripts/qa.js setup.
npm run dev        # nodemon server.js, default port 5000
npm start

# customer-app / gullyeats-admin
npm run dev
npm run build
npm run lint       # customer-app only (ESLint); the admin app has no linter

# frontend / ordering (Flutter)
flutter pub get
flutter run
flutter analyze
flutter test
flutter test test/responsive/screens_responsive_test.dart --plain-name "signup"   # one screen
flutter test test/responsive --update-goldens   # after an intended visual change
flutter run -t tool/screen_gallery.dart          # every screen with sample data, on a device
```

`frontend/test/responsive/` renders every onboarding screen at 6 phone/tablet sizes, at 1.3× and 1.5× system text size, in landscape and with the keyboard open, and fails on any layout error (overflow, unbounded constraints). For the small phone, standard phone, tablet and small phone at 1.5× text, it also compares each screen with a reference image in `test/responsive/goldens/`. A failed comparison writes diff images to `test/responsive/failures/`, which is gitignored. The goldens were generated on Windows, and font rendering differs on macOS and Linux, so regenerate them with `--update-goldens` before comparing on another OS. Add `--dart-define=SHOTS=<dir>` to also save a PNG for every screen and size. Add new screens to the `screens` list there. `ordering/test/responsive/` is the same harness for the vendor app: a fake backend (`fake_backend.dart`) answers its requests with sample data, it also renders Kannada and Tamil (using Windows' Nirmala UI font as the phone's fallback), and it stubs the Razorpay plugin. QA end-to-end tests for both web apps, the API and cross-app flows live in `customer-app/e2e` (Playwright, `npm run test:e2e` in `customer-app/`): it starts its own backend on :5050 (on the DB in `backend/.env`) and the two web apps on :5183/:5184, onboards a throwaway vendor (phones start `00999`) and deletes everything it made at the end (`node scripts/qa.js cleanup`). Run `node scripts/qa.js setup` in `backend/` once first: it creates the QA admin and writes its login to `customer-app/e2e/qa-secrets.local`. Device tests for both Flutter apps are in `<app>/integration_test/` (see each file's header): start a backend on :5050, `adb reverse tcp:5050 tcp:5050`, then `flutter test integration_test -d <device> --dart-define=API_BASE_URL=http://localhost:5050/api` (both apps read `API_BASE_URL`, defaulting to their hardcoded URL). The onboarding test needs location granted with `adb shell pm grant com.gullyeats.onboard android.permission.ACCESS_FINE_LOCATION` after the test installs the app (the install resets it), and the vendor test needs `QA_ADMIN_EMAIL`/`QA_ADMIN_PASSWORD` defines. The test inventory is `docs/qa/test-inventory.xlsx`, generated from `docs/qa/inventory.py`. The backend `npm test` runs `node:test` with stubbed models.

Vendor-app text lives in `ordering/lib/l10n/app_{en,hi,kn,ta}.arb`; run `flutter gen-l10n` after editing them. Screens read it as `context.l10n.<key>`, and code without a `BuildContext` uses `LanguageProvider.strings`. Compare order statuses with the server's codes (`"SERVED"`), never with translated labels.

The vendor app has a light and a dark theme (dark by default, switch on Profile, `ThemeProvider` saves it). The onboarding app has the same pair (it follows the phone's setting until someone taps the sun/moon button that `BaseScreen` puts at the top right of every step screen); its QR poster is always light, since it is printed. `AppColors` neutrals (`background`, `surface`, `black` = main text, `greyNNN`, `lightOrange`) are getters that follow `AppColors.dark`, so they can't sit inside `const` widgets. `AppColors.white` is always white: use it only for text/icons on orange or coloured fills, and `surface`/`background` for cards and pages. The goldens are light; `--dart-define=DARK=true --dart-define=SHOTS=<dir>` renders every screen dark to look at.

`tool/screen_gallery.dart` (debug builds only) opens each screen with sample data and never logs in. Switch screens with `adb shell "run-as com.gullyeats.onboard sh -c 'echo <index> > files/gallery_index'"`.

Flutter work uses the official `dart-flutter` Claude Code plugin (`claude plugin marketplace add flutter/agent-plugins`, then `claude plugin install dart-flutter@dart-flutter`). It provides the Flutter skills (for example `flutter-build-responsive-layout`, `flutter-fix-layout-issues` and `flutter-add-widget-test`) and the Dart/Flutter MCP server (`dart mcp-server`). The MCP server can launch the app, read runtime errors, inspect the widget tree and hot reload.

## API base URLs (hardcoded)

Domains: `gullyeats.in` = customer app, `admin.gullyeats.in` = admin (both Vercel), `api.gullyeats.in` = backend (Render custom domain). The old `gullyeats.vercel.app`, `gullyeats-admin.vercel.app` and `gullyeats.onrender.com` stay live and allowed (printed QR posters and installed Flutter apps use them). The first entry of `FRONTEND_URL_CUSTOMER` is the address new QR posters open.

Every client points at the deployed backend by default, so check these before testing locally:
- `frontend/lib/core/constants/api_constants.dart` and `ordering/lib/core/constants/api_constants.dart` (`baseUrl`)
- `customer-app/src/constants/api.js` (`API_BASE_URL`, overridable with `VITE_API_BASE_URL`; the Socket.IO URL comes from stripping `/api` off it)
- Admin dashboard filters live in each page's URL, never in the top bar or Redux: `hooks/useUrlState.js` (`useUrlState`, and `useRange` for the one date control, `components/DateRange.jsx`: Today / 7 days / 30 days / This month / Custom, plus "All time" on lists) and `hooks/useSearchBox.jsx` (`?q=`, searched on the server for paged lists). The backend reads the same `range`/`startDate`/`endDate` through `utils/dateRange.js`. The Dashboard is always today; Revenue (which absorbed Analytics) and the Business GullyPlay/GullyPulse tabs follow their date control. Sidebar badges come from `GET /api/admin/todo`.
- `gullyeats-admin/.env` (`VITE_API_URL`, `VITE_ADMIN_PATH`, `VITE_CART_PATH`; see `.env.example`). `VITE_API_URL` is used only by `npm run dev`: a production build calls its own site, and `gullyeats-admin/vercel.json` passes `/api/*` on to the Render backend, so the admin login cookie is first-party (browsers that block third-party cookies otherwise bounce the admin back to login)

## Backend architecture

- `server.js` wires everything together. Routes are mounted under `/api/{vendors,carts,orders,payments,admin}` and are implemented as `routes/*Routes.js` → `controllers/*Controller.js`. Handlers are wrapped in `utils/asyncHandler`. To return an error, set `res.status(code)` and then `throw new Error(msg)`; `middlewares/errorHandler` turns that into `{ success: false, message }`.
- **The Razorpay webhook must stay registered before `express.json()`.** It needs `express.raw` so the HMAC signature check runs on the raw request bytes. The JSON body limit is `10kb`.
- CORS uses an allowlist built from `FRONTEND_URL_CUSTOMER` and `FRONTEND_URL_ADMIN` (comma-separated) plus `http://localhost:5173`. Requests with no `Origin` header (the Flutter apps) are allowed.
- Auth: vendors and staff log in with phone + OTP + PIN (`vendorRoutes`). `middlewares/auth.js` reads `Authorization: Bearer <jwt>` and sets `req.user = { _id, role }` (role is one of `vendor | staff | admin`). Many cart, menu and order routes are deliberately **unauthenticated**, since the customer web app calls them without logging in. Admin login sets a `token` cookie. Cart routes check access with `utils/cartAccess.js`: `findManagedCart` lets in the owner, an admin or the cart's staff (orders, stock, open/close, fee lock status); `findOwnedCart` refuses staff (menu edits, cart details, sales, fee bills and payment, staff logins). The vendor app hides those screens for staff and shows a Handover tab (today's collected / to collect / refunded) in place of Sales.
- Real-time: `req.io` is attached to every request. Vendor clients join the room `<cartId>` (`join_vendor`). Customers join `order:<id>` (`join_order`). Controllers emit `new_order_received`, `order_updated` and `order_cancelled` to these rooms.
- Billing lock: carts owe GullyEats a daily `platformFee` that is summed from their orders over IST calendar days (`utils/cartPaymentLock.js`, 26h grace period). One payment settles every unpaid finished day at once (`getOpenBill`: oldest unpaid day through yesterday; `Payment.fromDate`..`billingDate`), so a vendor who pays late after selling past midnight isn't locked again right after paying. Checkout replaces a pending payment whose bill has changed (marked `EXPIRED` after checking Razorpay); an online payment that still arrives for it is refunded like a duplicate. `middlewares/cartPaymentLock.js` returns 403 with the lock status when a cart has unpaid fees. `Payment` documents are owner→platform fee payments, not customer payments.
- Platform fee per order: one value in the `Setting` document `_id: 'global'` (`utils/platformFee.js`, default ₹2, whole rupees 0–100), set from the admin Collections page (`GET/POST /api/admin/settings`, logged as `SET_PLATFORM_FEE`). `createOrder` copies it onto the order, and an edit keeps the order's own fee, so a change never alters old orders, bills or reports (they all sum `Order.platformFee`). `get-cart` and `get-menu-items` return the current `platformFee` for the apps' totals; never hardcode it in a client.
- Push notifications. **Vendor app** (Firebase Cloud Messaging, `utils/push.js`): a QR order pushes "New order #N · cart" to the cart's owner and staff (from `createOrder`), and `utils/feeReminders.js` (a 10-minute timer started in `server.js`) pushes owners "Platform fee due" between midnight and the 2am lock and "Cart locked" from 9am to 9pm, once per kind per cart per IST day (claimed in `Cart.feeReminder`). The app (`lib/core/utils/push.dart`) registers on the welcome screen and posts its Firebase Installation ID to `POST /api/vendors/push-id` (`User.pushIds`); logout unregisters it, and the server drops IDs Firebase reports as dead. Tapping a fee reminder switches to its cart and opens the payment screen (`Push.feeTap`, handled in `HomeScreen`). Android channels come from `MainActivity.kt`: `new_orders` (alarm sound `res/raw/paid.wav`) and `fees`. Needs `FIREBASE_SERVICE_ACCOUNT` (the service account JSON, or a path to it). The app's ID is `com.gullyeats.vendor`, matching `ordering/android/app/google-services.json`. **Customer app** (standard Web Push, `utils/webPush.js`, VAPID keys `WEBPUSH_PUBLIC_KEY`/`WEBPUSH_PRIVATE_KEY`/`WEBPUSH_SUBJECT`): the token page's "Notify me when it's ready" (automatic once allowed) saves a subscription on the order (`POST /api/orders/push-subscribe/:orderId` with `X-Gully-Order`, `Order.pushSubscription`), and serving it or a vendor cancel pushes it; `public/sw.js` shows it and a tap opens the order's page. Works in Chrome/Firefox on Android and desktop, on iPhone only from a home-screen app. Without the keys either kind of push is skipped.
- Area alerts (`controllers/areaAlertController.js`, `/api/carts/area-alerts/:cartId`): a vendor or staff member warns every cart within 1 km of their cart's saved location (`EVICTION | ROAD_BLOCKED | RAIN | CROWD`), by FCM push (channel `area_alerts`) and the socket event `area_alert` to each nearby cart's room. One per cart per 30 min; an alert shows for 1 hour and each other vendor's "I see it too" restarts the hour. A cart is pushed only for the first active report of each kind near it (later ones just refresh its app), and the app groups reports by reason (`groupAreaAlerts`: one row per reason with a vendor count), so a vendor sees at most 4 alerts and 4 notifications. The sending cart is never named. Rows (`AreaAlert`) are kept 90 days as a record of where drives happen. Framed as vendors helping each other: never a police tracker or a legality claim. The vendor app shows them as banners on Home (`lib/features/alerts/`) and sends them from the Orders screen.
- Main-road warning (onboarding app, Enable Location): `GET /api/carts/main-road?lat=&lng=` (auth) says whether the spot is within 25 m of an OpenStreetMap motorway/trunk/primary/secondary road (`utils/mainRoads.js`), and the app shows "Near a main road" under the map. A risk hint only, never a legality claim, and a failure shows nothing. The roads are a saved copy, `data/blr_main_roads.json` (Bengaluru only), because the free Overpass service is too slow to ask live; refresh it with `node scripts/fetch-main-roads.js`.
- GullyWeather (vendor app Orders strip): `utils/weather.js` fetches a 3x3 grid over Bengaluru from MET Norway (`api.met.no` Locationforecast, one request per point, plus today's sunrise/sunset from its Sunrise API) every 30 min (started in `server.js`; last result kept in `WeatherCache`), and `GET /api/carts/weather/:cartId` returns the cart's nearest point (data older than 2 h is `null`, never shown as current). MET is free for commercial use under CC BY 4.0: keep the "MET Norway" credit in the sheet and the identifying `User-Agent`, and keep requests light. It gives rain as mm per hour (no rain chance for India), so the app shows it as words (`rainWord`: none, drizzle under 2.5 mm, rain under 7.6 mm, heavy) and mm per hour, never an invented percentage. Forecast only, never an official warning. The app (`lib/features/weather/`) draws Sunny (squirrel, sunrise to sunset) and Chill (penguin, after sunset, and by day in heavy rain) in code (`characters.dart`); `MoodPicker` (`mood.dart`) picks the character and outfit, holds a weather-driven swap until a second update agrees, and shows both asleep once the cart is closed after sunset. The sheet's evening card ("Today so far", owners only) sums today's PAID/SERVED orders from `OrderProvider` and reads the existing fee status; it changes no billing. `--dart-define=WEATHER_PREVIEW=<mood>` forces a mood in debug builds; `test/weather/goldens/characters.png` shows every mood.
- Admin notifications (Notifications page, bell in the top bar, toast): `utils/adminNotify.js` `notifyAdmins({ type, title, text, to, key? })` saves a `Notification` (60-day TTL; a repeated `key` is skipped; `readBy` per admin) and emits `admin_notification` to the Socket.IO room `admins`. It never throws or blocks the request, and does nothing when Mongo isn't connected (stubbed tests). Raised from: word-filter review and report-hidden posts, a customer's refund flag, a failed auto-refund, a dish reaching `MIN_CARTS`, a new cart, a 1–2★ rating, and a 10-minute timer (refunds still owed after 2h; one overdue-fees summary per IST day from 9am, and each cart the Fee leakage tab flags, once per IST week, from `leakReport()`). The dashboard joins the room with a one-minute token from `GET /api/admin/notifications/socket-token` (signed with `JWT_SECRET + ':admin-socket'`, so it is not an API login), connecting straight to `VITE_SOCKET_URL` (default `https://api.gullyeats.in`) because Vercel's `/api` rewrite can't carry WebSockets.
- Uploads: images and QR codes go to S3 through presigned URLs (`utils/s3Client.js`). Each cart's files live under `carts/<cartId>/`: `photo` (one fixed name whatever the format, URL carries `?v=`), `qr.png` and `menu/<uuid>.<ext>`; shared dish photos are `dish-images/<slug>.jpg`. Dev and prod share the bucket. Order numbers come from the `Counter` model (`utils/getNextOrderNumber.js`).
- Menu item names: `name` is English. `names.{hi,kn,ta}` holds the same name written in each script, by sound, never translated. `utils/transliterate.js` fills it on save. It looks the name up in `FoodName` first, a list of about 1,200 common items with checked spellings (`data/food_names.json`, loaded with `node scripts/seed-food-names.js`; reseeding skips entries marked `reviewed`), then in the `Transliteration` cache. Any other name is spelled word by word, from `data/food_words.json` (common words, corrected by hand where Google is wrong) and Google Input Tools (unofficial and free, no key) for words not in it. A failed request never blocks a save. Orders copy `names` like `name`. The vendor app shows `displayName`, suggests names from `GET /api/carts/food-names` as the vendor types on Add Item (the onboarding app's Add Menu screen does the same, in English), and lets vendors correct the spelling in the edit dialog. To fill names on old items, run `node scripts/transliterate-menus.js`. `node scripts/fill-dish-images.js [--dry]` gives listed dishes without a photo one from TheMealDB or Openverse (only when its title or tags hold the dish's whole name), crediting each photo in `data/dish_image_credits.json`. New names that aren't in `FoodName` are tracked per cart in `DishCandidate` (`utils/dishCandidates.js`, keyed by `dishKey()`, which drops sizes and "spl"); once 3 different carts use one it appears on the admin Dishes page (`/api/admin/dishes`), where an admin fixes the spellings, can pick one of 5 Pixabay photos (`PIXABAY_API_KEY`; copied to S3 `dish-images/<slug>.jpg`, stored on `FoodName.image` as a key, not a URL, for a later CloudFront move) and approves, merges it as an alias (`FoodName.aliases`) or rejects it.
- GullyPulse (anonymous confessions, `/api/confessions`, customer pages under `/confessions`): a customer proves they ordered with `X-Gully-Order: <orderId>.<accessKey>`. The key is a random secret that `createOrder` returns only to customer QR orders (`Order.accessKey`, `select: false`). The customer app keeps it in `cart.orders`. Likes, reports and bans key on `authorKey`, an HMAC of the order's phone (or the order id when no phone was given). Public responses go only through `toPublic`/`commentToPublic` and never carry ids that identify the poster. `utils/wordFilter.js` + `data/blocked_words.json` decide BLOCK / REVIEW / ALLOW. Four unique reports hide an item (status `REPORTED`). Admins act through `/api/admin/moderation/*` (Moderation page), and every action is logged in `AdminAction`. The feed sorts by a stored `hot` score (`utils/confessionScore.js`); update pipelines need `{ updatePipeline: true }` in Mongoose 9.
- GullyPlay (games `nebula` = Nebula Rush, `reflex` = Zero Reflex, 30 s of tap-by-the-rule with "both" and "anything but a shape" rules from 8 s, golden stars, a Surge (x2) in the last 5 s and a daily twist (tiny, rush, blackout, drift), and `synapse` = Synapse, a 45 s memory game: repeat a growing chain of neurons where only the new link fires (whole chain on the first, reverse and after a miss), lengths 6, 10, 14 backwards, a speed bonus, a shield every 3 clean chains, a Surge (x2) in the last 10 s, a daily twist (silent, shuffle, mirror, ghost), three misses end it; `/api/games/:game/{scores,leaderboard}`; customer page `/c/:cartId/order/:orderNumber/play/:game`, picked from the token page): same `X-Gully-Order` identity as GullyPulse, one best score per player per game per IST day (`GameScore`), players shown only by an alias made from `authorKey`. Each game's rules are a pure module in `customer-app/src/game/<id>.js` (seeded by the IST date so everyone gets the same round; `node --test "src/game/*.test.js"`), described for the shared arcade page (`pages/Play.jsx`: loop, pause, food-ready banner, results, leaderboard, sound) in `game/catalog.js`. Engines report what happened in `game.events` (`{ type, ... }`), which the page plays through `game/audio.js` (all sound synthesised with Web Audio, no files; mute is remembered). To add a game: a module with `LIMITS`, a catalog entry, and a `GAMES` entry in `backend/controllers/gameController.js` whose `limits` equal the module's `LIMITS` (a backend test compares them). Scores come from the phone, so the server only refuses impossible ones: never tie rewards to the boards. A player who ordered without a number can add one from the game (`POST /api/games/phone`, only for an order with none): it becomes their identity across orders and carts, and that order's scores move to it, keeping the better one per day. Nebula Rush is a 55 s round in four sectors ending in a Mothership boss, with a Nova bomb (double-tap) and a daily anomaly, all from the seed and the clock (never from play, or players stop meeting the same round). Its pilot XP, daily missions and skins (`game/pilot.js`, stored by `utils/play.js`) live on the phone and are cosmetic only: they must never change play or score. The arcade opens on a lobby (anomaly, missions, skins, reduced motion and vibration settings).
- Admin Business page tabs GullyPlay and GullyPulse (`/api/admin/insights/{play,pulse}?days=7|30`) count anonymous players and posters: they match `authorKey` against keys recomputed from the window's QR orders, and never return keys, phones or order ids. `GameScore.rounds` counts every accepted round (rows from before it count as 1).
- `Cart.location.coordinates` is stored as `[lat, lng]`, not the GeoJSON `[lng, lat]` order, so there is no `2dsphere` index on it (one refused carts east of 90°E; `scripts/drop-cart-geo-index.js` drops it from an old database).

## Flutter apps

Both apps use the same structure: `lib/core/` (constants, routes, theme, widgets, utils) and `lib/features/<feature>/{models,providers,services,screens|presentation,widgets}`. State management uses `provider` with `ChangeNotifier`s that are registered in `main.dart`. Services make HTTP calls using `ApiConstants`. Tokens are stored in `shared_preferences`. Both apps are locked to portrait mode and use the Poppins font. In `frontend/`, screens are built on `core/widgets/base_screen.dart`, which caps content at 500px wide. With `expandToFullHeight: true` the child gets a bounded height, so it must scroll itself (a `ListView` or a `SingleChildScrollView`). Step screens put their main buttons in `AppFooter`, passed as `bottomNavigationBar`. **UI rules for both Flutter apps (tokens, layout, feedback, responsive and async rules, and a checklist for porting them to `ordering/`) are in `docs/ui-guidelines.md`.** Only `ordering` uses `socket_io_client` (in `OrderProvider`) and `razorpay_flutter`.

## Admin dashboard domain mapping (from gullyeats-admin/README.md)

- Cart status: LIVE = `isOpen`. PAUSED = closed and `isActive === false`. ATTENTION = the cart has a PENDING platform-fee `Payment`. Anything else is OFFLINE.
- Order status: PENDING = awaiting payment, PAID = preparing, SERVED, CANCELLED. "Preparing" is not a status: the vendor app can set `Order.preparingAt` on a PAID order (`PUT /api/orders/preparing/:orderId`), which billing and sales ignore. The customer token page shows Placed → Paid → Preparing → Served and the cart's queue from `GET /api/orders/queue/:orderId`: paid, unserved orders from the last 12h in payment order, with only token numbers of others. Every order change emits `queue_changed` (no payload) to the Socket.IO room `queue:<cartId>`, which customers join with `join_queue`.
- GMV = the sum of `totalPrice` over paid orders (`PAID` or `SERVED`). Platform revenue = their `platformFee`. Unpaid and cancelled orders count toward order totals only. The vendor sales report and fee billing use the same rule.
- Customers can rate a served order 1–5 stars (`Order.rating`) and/or leave text (`Order.feedback`) through `PUT /api/orders/submit-feedback/:orderId`. The admin feedback list shows both; insights views still show counts and rates. The customer app keeps a summary of every order placed on the phone (`cart.orders` in redux-persist), so the menu and welcome pages link back to open orders after the back button, a closed tab or a re-scan.
